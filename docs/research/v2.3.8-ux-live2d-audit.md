# ReadMD V2.3.8 Skill UX 与 Live2D 桌宠上游审计

审计日期：2026-08-31
配套清单：[v2.3.8-ux-live2d-audit.json](./v2.3.8-ux-live2d-audit.json)

## 结论先行

本次共审计 26 个仓库，覆盖 Skill 管理/导入、透明桌宠窗口、Live2D 渲染、拖放和批处理。每个仓库都固定到审计时的远端 `HEAD`，许可证只按该 revision 中能够实际找到的文件或元数据记录；README 徽章不能自动视为完整再授权。

可以直接用于 ReadMD 决策的结论是：

1. Skill 导入应当保留完整目录，以“来源预览 → 校验 → 差异确认 → 可恢复落盘”为唯一入口；GitHub、本地文件夹和 ZIP 只应是三个输入适配器，不能各自拥有一套安装逻辑。
2. 桌宠不应引入 Electron、Tauri、Godot 或 PySide6 第二运行时。ReadMD 已使用 pywebview 和原生 WebView2/WKWebView/WebKitGTK，应先验证同进程第二原生窗口是否能满足透明、置顶、点击穿透和拖放；验证失败的平台不能用浏览器窗口冒充原生支持。
3. Hermes 的 MIT 代码可以作为协议和算法参考，但它安装的 Petdex/Hermes 角色素材没有随 `pet.json` 提供可验证的许可证。现有 Hermes 角色图、缩略图和第三方角色不得复制到 ReadMD。
4. `pixi-live2d-display` 的 MIT 只覆盖包装库，不能覆盖 Cubism Core、SDK Components 或模型素材。Live2D 官方条款不是普通 MIT/Apache 依赖；正式发布前必须完成独立许可判断。
5. GPT Image 2 能生成和编辑图像，但 OpenAI 官方文档没有提供分层 PSD、Cubism 参数、骨骼绑定、物理设置或 `.moc3` 导出能力。因此它只能用于原创设定稿、表情和拆层参考，不能被描述为“自动生成可发布的 Live2D 模型”。[OpenAI 官方 GPT Image 2 文档](https://developers.openai.com/api/docs/models/gpt-image-2)

## 研究方法与边界

- Revision 通过 `git ls-remote --symref <repo> HEAD` 获取，并记录完整 40 位 commit。
- 许可证优先读取固定 revision 的 `LICENSE*`；仅存在 `package.json`、`pyproject.toml` 或 README 声明时标记为“元数据/README 声明”，不据此复制代码。
- 研究只做只读源码、README 和许可证审计，没有把任何上游仓库、素材或构建缓存写入 ReadMD。
- 这是发布前工程和许可分流，不是法律意见；Live2D 适用许可应由权利方书面确认。

## Hermes Pet 机制专项结论

Hermes 上游当前协议的有价值部分是：

- 一个 Pet 是 `pet.json` 加 `spritesheet.webp/png`。当前图集为 8 列 × 9 行、每格 192×208，总尺寸 1536×1872；旧版还兼容 9 列 × 8 行。
- 状态映射是单向状态机，错误、完成庆祝、挥手、等待输入、工具执行和 review 等信号按优先级选出唯一动画行。ReadMD 可以采用同样的“业务状态与渲染分离”，但应使用自己的状态名和实现。
- 下载逻辑会把素材 URL 限定在 Petdex 域名，能减少 SSRF 风险；生成流程把非确定的图像输出经过分帧、边缘背景清除、尺寸归一、缺帧检查和确定性图集拼装。
- Hermes 的 AI 生图流程仍然生成的是像素图行和图集，不是 Live2D 的分层、参数化和绑定模型。

不能复用的部分同样明确：

- Hermes 仓库的 MIT 授权覆盖仓库代码，不自动覆盖 Petdex、用户安装目录或其他来源的角色图片。
- 当前 Pet 元数据只要求 ID、名称、描述和 spritesheet 路径，没有强制 `author`、`license`、`source_url`、`source_sha256`、`redistribution`。这不足以成为 ReadMD 的可发布素材契约。
- 本机 Hermes 安装中发现的角色包与缩略图没有随包提供独立 LICENSE/NOTICE；因此审计没有复制、散列入库或展示这些素材。

若未来 ReadMD 支持可安装角色包，元数据必须增加：

```json
{
  "id": "readmd-original-pet",
  "format_version": 1,
  "author": "...",
  "license": "LicenseRef-...",
  "source_url": "...",
  "source_revision": "...",
  "source_sha256": "...",
  "redistribution": "allowed",
  "runtime": "live2d-cubism-5",
  "entry": "model/readmd.model3.json"
}
```

首发不应开放第三方角色导入；先只允许一个 ReadMD 自有原创模型，避免把尚未解决的模型版权和“Expandable Application”许可问题扩大成公共导入面。

## Live2D 与 GPT Image 2 的真实边界

官方 Cubism 资料明确区分：

- Cubism Web/Native Framework 与 Samples 属于 Live2D Components，适用 [Live2D Open Software License](https://www.live2d.com/eula/live2d-open-software-license-agreement_en.html)。
- Cubism Core 不发布在 GitHub，适用 [Live2D Proprietary Software License](https://www.live2d.com/eula/live2d-proprietary-software-license-agreement_en.html)。[官方 Core 说明](https://docs.live2d.com/en/cubism-sdk-manual/cubism-core/)
- 发布使用 SDK 的内容可能需要 Publication License；个人和小规模业务通常有豁免，但“Expandable Application”被官方明确列为例外并需要专门审核。[官方发布许可说明](https://www.live2d.com/en/sdk/license/)
- 模型、纹理、动作、声音与角色设计各自需要权利链。官方 sample model 也有 Free Material License 和逐模型条款，不能当作公共领域素材。

因此，ReadMD 在下列证据齐全前不能发布 Live2D 桌宠：

1. Live2D 对 ReadMD 的发布形态、是否属于 Expandable Application、Core/Components 随安装包分发方式给出可归档的书面适用结论。
2. 软件内 NOTICE、最终用户条款和 SBOM 覆盖 Components、Core、Pixi 包装层及所有模型文件。
3. 原创模型权利包包含：设定与拆层源文件、Cubism 工程源文件、运行时导出、作者/委托合同、第三方素材声明、提示词/人工修改记录和逐文件 SHA-256。

GPT Image 2 可以参与“设定草图 → 表情草图 → 人工重绘拆层”的前两步。真正的 Live2D 交付仍需要人工建立眼睛、嘴、头发、身体等独立图层，在 Cubism Editor 中建立参数、deformer、物理、动作和表情，最后导出 `.model3.json`、`.moc3`、纹理、motions、expressions 与 physics。图像生成成功不能替代这些验证。

## 推荐架构

### 1. Skill 导入

```text
GitHub URL ─┐
文件夹 ─────┼─> SourceAdapter ─> BundleScanner ─> SafetyValidator
ZIP ────────┘                                  │
                                               v
                          Preview/Diff ─> explicit confirm ─> SkillStore
                                                               │
                                           provenance + hashes + rollback
```

- 三种来源共享扫描、路径归一、文件数量/体积限制、脚本禁用、许可证检查、冲突策略和版本快照。
- UI 默认只读展示用途、变量、示例、来源、许可证和文件树；编辑是显式二级动作。
- 私有 GitHub 凭据仅在匿名请求收到认证错误后出现，配置只保存 `credential_id`。
- 后端只返回稳定错误码；所有用户文案由 46 个 locale 映射。

### 2. 桌宠运行时

```text
ReadMD Core process
├─ PetController      状态机、节流、位置、减少动画
├─ PetTaskQueue       复用现有打开/转换/OCR/剪贴板能力
├─ PetRenderer        延迟加载 Live2D；渲染器不接触文件系统
└─ PetWindowAdapter
   ├─ Windows WebView2 native adapter
   ├─ macOS WKWebView native adapter
   └─ Linux WebKitGTK native adapter
```

- 保持同一 Python 进程和现有 pywebview 技术栈；不启动本地控制端口，也不新增 Electron/Tauri/PySide sidecar。
- 桌宠默认关闭。打开后才创建第二原生窗口并加载模型；首屏、编辑器启动和离线基础功能不得加载 Cubism/Pixi/模型资源。
- 30fps 是上限；空闲降频，减少动画模式显示静态姿态。模型加载失败只关闭桌宠，不能影响主窗口或文档保存。
- 拖入文件和双击剪贴板只产生规范化任务，实际打开、转换、OCR、批处理仍调用 ReadMD 现有能力，避免第二套格式路由。
- 模型、Core 和 JS 全部本地加载并固定 hash，运行时不访问 CDN、Petdex 或第三方模型站。

这个架构仍需要原型验证。pywebview 的透明、点击穿透、拖放和多显示器行为在不同后端不完全等价；如果必须依赖未公开的 backend 内部对象，应该视为维护风险并停止发布，而不是静默切到浏览器窗口。

## Release blockers

| 严重度 | 阻断项 | 退出条件 |

## 发布前验证清单
